The proposal is a hypothesis for early-stage startups: separate the software development unit from the processing and scaling unit. Modules remain the cohesive units for organizing code, business rules, dependencies, persistence, tests, and evolution, while individual use cases may adopt distinct execution, deployment, and scaling strategies when concrete workload characteristics justify doing so.

A modular monolith is appropriate when a small team needs clear software boundaries without distributed-system overhead. Microservices provide stronger deployment, operational, organizational, and scaling independence, but introduce network communication, timeouts, retries, distributed transactions, observability, partial failures, and additional infrastructure and operational work. These architectures optimize different properties rather than necessarily representing sequential maturity stages. The proposed architecture targets the space where modularity is valuable but some workloads have substantially different processing requirements.

For example, an `Orders` module could contain `CreateOrder`, `CancelOrder`, `GetOrder`, and `GenerateReport` while assigning different execution strategies: `CreateOrder` and `GetOrder` might run as functions, `CancelOrder` in a conventional application, and `GenerateReport` asynchronously. If `GetOrder` experiences substantially higher demand, it can be scaled independently without replicating or converting the entire `Orders` module into a service. Distribution applies to the execution of a use case rather than necessarily to the module itself.

The initial system can remain entirely within a single process. A use case distributed to a function can still invoke other modules through in-process libraries. Module boundaries therefore do not automatically become network boundaries. Asynchronous interactions can use queues or streams when appropriate, but distributed communication is introduced only where its benefits justify its costs. A use case can eventually run in a function, container, conventional application, worker, or another mechanism appropriate to its workload.

The architecture also distinguishes shared capabilities by scope. Truly universal capabilities can belong to a common core; capabilities used by several modules should preferably remain in their own module rather than being absorbed into a generic core; capabilities specific to one context remain with that consumer module. This avoids turning the core into a repository of generic abstractions. For example, if `Orders` and `Payments` both depend on pricing, `Pricing` can remain an independent module rather than becoming part of the core.

Functions are proposed as a possible default for synchronous use cases in an early-stage startup because they can provide on-demand processing, independent scaling, and low idle capacity under low or variable utilization. This is not an assertion that functions are inherently cheaper or superior. Constant, predictable, or latency-sensitive workloads may favor provisioned containers or conventional processes. Cold starts can also make functions unsuitable for some workloads. The intended principle is to begin with a simple execution strategy and change it when actual workload data demonstrates that another strategy is more appropriate.

The central economic and architectural objective is to defer infrastructure decisions until real demand provides evidence. Rather than provisioning the entire application for hypothetical future growth, the system can initially use capacity compatible with current demand and selectively change execution strategies as workloads reveal different requirements. This does not guarantee lower cost: provisioned infrastructure can be cheaper for sustained workloads, and finer-grained execution can increase duplicated runtimes, memory consumption, startup overhead, deployment complexity, and total operational cost. The relevant comparison must include infrastructure, observability, deployment, maintenance, and engineering time.

The approach allows selective evolution:

`modular monolith → selective distribution → additional distribution when justified`

A product can remain mostly in one process while only workloads with distinct scaling, latency, processing, or cost requirements are distributed. For example, an AI workload with specialized computational requirements can use dedicated infrastructure while ordinary CRUD operations remain conventional. Distribution should therefore be treated as a local decision rather than a property automatically inherited by an entire module.

The proposal does not eliminate distributed-system complexity. Once a use case executes outside the main process, latency, timeouts, retries, idempotency, observability, and partial failures become relevant. Its intended benefit is containment: ten use cases can remain local while an eleventh incurs distributed-system complexity only if that eleventh workload has a sufficiently strong reason. The architecture seeks to introduce complexity selectively rather than universally.

Module dependencies remain significant. Library-based dependencies preserve in-process calls and avoid network overhead, but reduce some deployment independence because incompatible changes require consumers to update, recompile, and test. Dependency direction should therefore be explicit and cycles avoided. Turning mutually dependent modules into separate distributed services could merely transform code coupling into network coupling. Likewise, distributing `Orders.GetOrder` does not require distributing `Customers.GetCustomer`; the latter can remain an in-process dependency until there is an explicit reason to separate it.

Fine-grained execution also has resource implications. Multiple functions or containers may replicate shared libraries and dependencies, increasing memory usage, startup time, and potentially processing cost. Independent scaling is also constrained by shared resources such as PostgreSQL, queues, caches, and external services. Scaling functions cannot overcome a database bottleneck and may intensify it. The architecture provides finer-grained processing capacity; it does not make underlying resources infinitely scalable.

Operational complexity is another trade-off. Different execution strategies increase deployments, configurations, permissions, infrastructure resources, and observability requirements compared with a conventional monolith. The architectural question is therefore not whether the approach is intrinsically simpler than either a monolith or microservices, but whether additional complexity is introduced only when a concrete workload need provides sufficient benefit to justify it.

The proposal is intentionally not classified as microservices. Microservices generally consolidate modularity, deployment, ownership, operation, and scaling into service boundaries. Here those decisions are deliberately decoupled. A module remains the unit of development and evolution; its use cases may share code, rules, dependencies, and tests while independently choosing execution strategies. A module may remain entirely inside a conventional application indefinitely, while another module may distribute only one operation.

The approach is not universally appropriate. A small application with predictable demand and infrastructure that comfortably handles the workload may gain nothing from this granularity. Systems with specialized security, availability, governance, auditing, isolation, or consistency requirements may require different architectural decisions. The intended context is specifically an early-stage startup with a small team, limited resources, initially low or variable demand, and potentially uneven growth among workloads.

The architecture remains an unvalidated hypothesis rather than an empirically established pattern. Its effectiveness would need to be evaluated by whether modules remain simple to develop and test despite different execution strategies; whether use cases can acquire independent scaling without forcing module-wide restructuring; whether the application can begin simply and distribute only selected workloads as concrete needs emerge; whether modules can continue using libraries without every boundary becoming a network boundary; and whether the economic benefit of workload-specific infrastructure exceeds the additional operational cost.

Long-term validation would also require observing organizational and architectural evolution. If growth eventually requires systematically rewriting modules, replacing dependencies with APIs, or migrating broadly to microservices, the architecture may merely have postponed complexity. If the system can instead evolve incrementally, distributing only workloads that justify distribution, that would provide evidence supporting the approach. Discovering that a traditional modular monolith provides equal or greater value would also be a valid experimental outcome.

The core hypothesis is therefore: software can potentially retain the simplicity and cohesion of modular development while allowing infrastructure and processing capacity to be provisioned at use-case granularity. The proposal does not seek to replace modular monoliths or microservices. It proposes an alternative starting point for a specific startup context, with the goal of deferring infrastructure and operational decisions until concrete workload characteristics justify them.
