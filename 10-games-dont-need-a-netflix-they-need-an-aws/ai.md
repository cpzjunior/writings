The introduction explains that the author’s experience with an Xbox Series S and an aging PC revealed two mismatches in the current gaming model: subscription catalogs contain far more games than the user actually wants to play, while local hardware must periodically be replaced to keep pace with increasingly demanding games. The author argues that the underlying need is neither a large game library nor permanent ownership of increasingly powerful hardware, but temporary access to sufficient computing capacity for whichever game the user chooses to play. This leads to the central question of whether cloud gaming has been framed incorrectly by treating games as the primary product rather than computing capacity.

The problem with turning games into Netflix is that the analogy between games and movies or television breaks down because games are executable applications rather than passive media. Video streaming mainly requires storing and transmitting content that has already been rendered, whereas cloud gaming requires servers to execute the game in real time, process user input, render frames, encode them, and transmit them with sufficiently low latency. Consequently, computing capacity is itself part of the product being delivered. A large game catalog also does not necessarily create proportional value because players may care about only a small subset of titles, while games demand significant time and learning investment compared with trying a new movie or series. Thus, if a user already owns or has chosen a particular game, the relevant problem may not be access to more games but access to the computational resources capable of running that game.

The AWS and GPU-as-a-service section proposes applying the logic of cloud computing to gaming hardware. Instead of purchasing a GPU or console expected to remain adequate for several years, players could rent different levels of computing capacity according to the requirements of the game and their desired graphical quality. A service could offer inexpensive, intermediate, and high-performance machines, with users paying through usage-based credits or potentially recurring plans centered on computing resources rather than catalog access. Under such a model, a player could use cheaper capacity for less demanding games and pay more when requiring advanced GPUs, high resolutions, high frame rates, or ray tracing. The economic distinction is that the user pays primarily for the resource actually consumed rather than for a large collection of games that may never be played, making computing capacity the unit of value while games remain the software being executed.

The hardware stops being a bet section argues that local hardware forces consumers to forecast future technological requirements. A console or GPU purchased today represents a commitment to a certain level of capacity for several years, and technological progress can gradually make that capacity insufficient even though the hardware continues functioning. Cloud gaming could transfer this obsolescence problem from individual consumers to infrastructure providers, which can introduce newer GPUs into datacenters while retaining older hardware for less demanding workloads. Obsolescence therefore would not disappear but would become an infrastructure-management problem handled at scale. The conceptual change is from predicting what hardware will be needed several years from now to consuming whatever computing capacity is appropriate for the game being played in the present.

The game and the machine do not have to be the same product section argues that cloud computing makes it possible to separate the software from the infrastructure required to execute it. A user could purchase games through existing ecosystems while using local hardware when adequate and remote infrastructure when it is not. This would mean that cloud gaming does not require a single “Netflix of games”: companies such as Sony, Microsoft, and Nintendo could continue competing through games, libraries, exclusives, and services, while independent providers could specialize in gaming infrastructure without owning game catalogs. Competition in the infrastructure layer could then focus on price, latency, GPU availability, geographic positioning, and operational efficiency, while the game layer remained a separate market. The underlying analogy with general cloud computing is that applications do not need to own or directly control the servers on which they run, so there is no fundamental reason games and gaming infrastructure must remain bundled.

The “What are we actually renting?” section distinguishes two products that current models often combine: access to games and access to the computing capacity required to run them. Game subscriptions address the first through software and content distribution, while cloud gaming addresses the second through remote infrastructure. These services could therefore be purchased independently: a player might buy a small number of games from one platform and rent computing capacity from another provider whenever local hardware is insufficient. This would create separate competitive layers, with game platforms competing over games, prices, exclusives, services, and libraries, and infrastructure providers competing over performance, price, latency, availability, and efficiency. The author concludes that cloud computing creates the possibility of reversing the traditional hardware relationship: rather than continually purchasing machines to keep pace with increasingly demanding games, users could rent the computing capacity necessary to run the games they choose, making an “AWS for games” potentially more fundamental than a “Netflix of games.”
